## 1. Interior character facets (SOLVED, owner confirmed the cure)
Symptom: indoors near lamps every triangle of a character (skin and clothes) showed flat with hard edges; gone with PBR off.
Cause: with the per-object (forward) lamp shadows on, Effects\PointShadows.fx still runs as the room darkening
(KeepDarkening); its per-lamp amount was falloff x N.L with N from TESR_NormalsBuffer (rebuilt from depth: flat per
triangle). Owner confirmed `[Shaders.ShadowsInteriors.Main] LampReachMask = true` cures it.
Fix (0026c5d, DLL only): ShadowsExteriorEffect::UpdateSettings sets TESR_PointShadowNear.z (the reach mask) whenever
`[Shaders.ShadowsInteriors.Forward] Enabled` is on. NOT yet confirmed in game with the rebuilt DLL.
Earlier wrong guesses, kept as options, now default OFF: `[Shaders.ShadowsInteriors.Forward] AutoNormalOffset` (7886e7f),
`[Shaders.AmbientLight.Main] NormalSmoothingWorld` (ae5d288).
Kept ON: `[Shaders.PBR.Main] SmoothObjectNormals` (4b6b26a, 8f86f11, f2382c3): object/skin shaders take the vertex normal
(not the ddx/ddy per-triangle one) for the sun-shadow offset, lamp-shadow offset, sky ambient and metal reflection.
Carried in TEXCOORD8 (3-lamp light-only passes), lightDistSq.w/lightDir.w octahedral (3-lamp full passes, replacing
METAL_UP's world-up; the metal sky test is now world-space), uv.zw octahedral (4-6 lamp passes, SkinVPSTemplate);
SKIN2001.pso reads its VS's normal. The shaders default it on (Shadow.hlsl OBJECT_SMOOTH_NORMALS 1); the DLL passes 0
when the setting is false. UNVERIFIED: compiled by the owner's build (they said it compiles), but no check of ps_3_0 input
counts (3-lamp full passes with PROJ_SHADOW now use exactly 10 inputs) or slot counts (six-lamp SLS2035 near the limit);
look for shader compile errors / driver refusals in the log.
Docs: docs/next/SMOOTH-OBJECT-NORMALS.md (incl. the resolution section).

## 2. Indoor lamp light: hard steps at tile/object edges, flicker with position (IN PROGRESS)
Cause (owner confirmed `[Shaders.PBR.Linear] ExactPassSums = 3` cures the steps): with linear lighting each extra lamp
pass and highlight pass was encoded on its own (enc(A)+enc(B) != enc(A+B)), and the game picks passes per object.
New problem with 3: floor rubble turns white. Owner: mode 1 (highlights only) does not whiten -> the lamp fold-in
(mode 2, core/PassSums.h Begin/End buffer) adds a run's light when the next HOOKED pass ends the run; some objects'
colour (texture multiply) pass apparently goes through an unhooked path, so the light lands after the colour.
Fix attempt (fd46ba3, DLL only, UNTESTED): PassSums::ModeFromSettings lets ExactPassSums 1 combine with LampSums
(`[Shaders.PBR.Main] LampSums = true`, restart to compile in; per-pass exact increments enc(dec(s)+L)-s, no deferred step).
Test: LampSums true + ExactPassSums 1, same spot: steps fixed and rubble normal? Known limit: LampSums exact for one extra
lamp pass per pixel (3-5 lamps); 6+ lamps can stay a bit bright. If rubble still whitens: find which pass draws the
rubble's colour (ExactPassSums logs runs for some frames after a mode change: "ExactPassSums run: ... ended by pass");
consider ending/skipping the run for alpha-blended objects.
Also noticed (not tested, may be separate): Main.Main.Performance LampScissor clips extra-lamp passes to a screen rect
from NiPointLight::Spec.r; a straight cut across several objects in the owner's screenshot might be that. Live test:
`LampScissor = false`.
